Status: PLANNING, 2026-11-09. Follows `docs/PLAN_GEOMETRY_AND_DENSE.md` section D. Every number below is frozen before the first run; a change needs a new dated section, not an edit. Camera poses and paths (`outputs/maps/mqg_sumida_0025_0125`, `mqg_fsc_campus_aerial`, global mapper) are a frozen baseline and are not re-estimated. Scale stays RELATIVE, NOT_NAVIGATION_SAFE.

**Problem.** `outputs/evidence/dense/sumida_sameview_v2.jpg`: trees, the elevated road and buildings are dense, the paved walkway in front of the camera is almost empty. Baseline (`dense_report.json`, v2): 117 reference views, 108 VERIFIED, 2,320,985 raw kept -> 917,498 fused, voxel 0.0302, 58.6 s. FSC: 145/145 verified, 1,942,876 fused, voxel 0.0143, 76.8 s. The goal is more of the *visible* floor and structure recovered, never more points where points already are. A larger total count, a bigger point size, duplicated points or a passing test never count as improvement.

## 1. Frozen measurement set-up (done once, before any pipeline change)

**Frames and regions.** Three Sumida frames: `f000240` (t≈8 s), `f000900` (t≈30 s), `f001560` (t≈52 s). On each full-resolution frame hand-draw polygons, stored in `outputs/evidence/dense_cov/regions_sumida.json` (`{frame, width, height, regions:[{name, class: floor|structure, polygon:[[x,y],...]}]}`, pixel coordinates of the stored JPEG; scaled by `work_width / width` for the 640 px stage maps):
- `floor`: paved walkway / asphalt path actually visible, one or two polygons per frame, excluding people, benches, bollards and the bottom 12 % band if a logo or caption sits there; the far-field floor beyond the first bench row is a separate polygon `floor_far` (reported, not part of the acceptance);
- `structure`: elevated road, buildings, lamp posts, tree trunks and crowns together (two to four polygons); sky and water are outside every region.
Polygons are drawn once, reviewed on the frame overlay `regions_overlay_<frame>.jpg`, and frozen; before/after use byte-identical JSON. `f000900` is not a reference view in the baseline run (neighbours 73 = `f000880`, 77 = `f000930`), so the measurement harness computes the stage maps for the three frames explicitly with the production neighbour rule, independent of the `max_pairs` subsampling; the production run is otherwise untouched.

**Short segment.** Sumida t = 4–14 s (`f000120`..`f000420`, 31 frames, contains `f000240`); expected runtime about 12 s. Every experiment runs here first; only the single minimal change that passes is applied to the full clip and to FSC.

**Stage metrics** (per frame, per region class, written to `stage_metrics_<run>.json`; "share" = pixels / region pixels at 640 px):
- S1 `cand`: share with a finite best-cost depth before any gate (every pixel that is not `borderValue`-invalid in all neighbours);
- S2 `conf`: share passing the confidence gate (`MAX_COST 0.35`, `MIN_MARGIN 0.02`, `TEXTURE_VAR 20`, interior plane); plus the breakdown of the rejections: `cost`, `margin`, `texture`, `boundary_near` (best plane = index 0), `boundary_far` (index 63), each as a share of region pixels, failures counted in that order (a pixel counts once);
- S3 `verif`: share of confident pixels surviving other-view verification, with the drop reasons `outside_partner`, `no_partner_depth`, `disagree`;
- S4 `fused_n`: raw count of fused points whose source pixel lies in the region (point carries `(ref, u, v)` of its source);
- S5 `cov1px`: share of region pixels hit when the full fused cloud is projected into the frame as a 1-pixel splat at 640 px, no dilation, hidden points not removed (reported separately with a 2-voxel z-buffer as `cov1px_zbuf`). Point size in any render used as evidence is fixed at 1 px.
Raw point counts (S4) and rendered pixel shares (S5) are always reported as separate columns.

**Error metrics** (per run, whole cloud and per region class where applicable):
- `inconsist`: share of verified points whose depth disagrees > 10 % with an independent held-out view: for a point from reference k, the held-out view is the registered frame nearest to k±5 that is neither k nor in the verifier set of k, sees the point (z > 0, projects inside) and has its own confident depth at that pixel. Only points with such a view enter the denominator; the share without any held-out depth is reported as `inconsist_unchecked`.
- `float_knn`: share of fused points with fewer than k = 4 other fused points within r = 2 voxels.
- `float_fs` (free-space violation): share of fused points for which at least one view that sees the point has a confident depth at that pixel greater than 1.10 x the point's depth in that view (the view looks *past* the point). A view whose depth is in front of the point is occlusion, not a violation, and is not counted.
- `sparse_agree`: the existing per-view gate stays at >= 0.70 unchanged; the median over verified views is also recorded.
- `seconds`: wall time of the full-clip run on the same machine; baseline 58.6 s (Sumida), 76.8 s (FSC).
Baseline run M0 = unchanged code with the harness, producing all metrics above for Sumida (segment and full) and FSC. Nothing else starts before M0 is on disk.

## 2. Acceptance of a change (all of the following, measured on identical inputs)
- Floor: `cov1px(floor)` up by >= +8 percentage points on each of the three frames and the three-frame mean >= 1.4 x M0; `fused_n(floor)` up on each frame (counts must move with the share; a share rise with flat counts means duplicates and is rejected).
- Structure: `cov1px(structure)` down by no more than 2 pp on any frame.
- Errors: `inconsist` up by no more than +2 pp and <= 15 % absolute; `float_knn` and `float_fs` up by no more than +2 pp each; every verified view keeps `sparse_agree` >= 0.70 and the median does not fall by more than 0.03.
- Time: Sumida full clip <= 3 x 58.6 s = 176 s.
- FSC regression (same change, same thresholds): `views_verified` >= 143 (baseline 145), fused points >= 0.9 x 1,942,876, `inconsist`, `float_knn`, `float_fs` not up by more than +2 pp, time <= 3 x 76.8 s.
- Evidence: `sameview_<frame>_<run>.jpg` with source / M0 dense / new dense side by side, same pose and FOV, 1 px points, region outlines drawn, caption with layer label and counts; `coverage_table.csv` with one row per (run, frame, class, metric).

## 4. What gets recorded
- `PASS`: all section 2 criteria met; the change becomes the default and `dense_report.json` records `coverage_plan: E-x adopted`.
- `FAIL`: run completed, at least one criterion missed; numbers stay in `coverage_table.csv`, code change reverted or kept behind a flag that is off.
- `NOT_ADOPTED`: PASS on the segment but FAIL on the full clip or on FSC (trade-off, with both tables), or PASS on coverage with a time overrun.
- `NOT_RUN`: the M0 trigger in section 3 was not met; the row says which share was below the trigger.
- `BLOCKED`: harness cannot compute a metric (e.g. no held-out view with depth for > 80 % of points -> `inconsist` BLOCKED, the run cannot PASS).
- Mesh stays `EXPERIMENTAL`, `visual_check FAIL`, until the radial streaks and holes have their own measured criteria; nothing in this plan changes the mesh.
Logs: `docs/VALIDATION_LOG.md` one row per run (run id, frames, floor / structure `cov1px` before -> after, `inconsist`, `float_knn`, `float_fs`, seconds, verdict); raw files under `outputs/evidence/dense_cov/`.

3. **Neighbour shortage on the forced frame.** If `f000900` has fewer than 2 neighbours inside the baseline/depth range [0.05, 0.30], the forced sweep uses the neighbours available (>= 1) and the metrics file says so; with 0 neighbours its S1–S3 are `BLOCKED` while `fused_n_proj` and S5 `cov1px` are still measured.
